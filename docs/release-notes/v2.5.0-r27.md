# v2.5.0-r27 — rekordbox playlists keep their track order

<!-- debs: rebuild -->

New Mixxx build. One import fix — nothing else changes.

- **Playlists imported off a rekordbox USB now keep their track order**
  (`rekordbox-playlist-order.patch`, patch 18). Opening a playlist used to
  jumble it — most visibly, the last ~10 tracks of the device turned up at the
  *top* of the playlist instead of wherever they belonged.

  When Mixxx reads a rekordbox device it stores every playlist entry keyed by
  rekordbox's `entry_index`, then reads them back by asking for the indices
  1, 2, 3 … N in turn. That only works if `entry_index` is exactly the run
  `1..N`. Real rekordbox exports don't do that — they write sparse and
  non‑1‑based `entry_index` values — so the read-back pulled tracks into the
  wrong slots and, for every index that had no match, silently inserted a blank
  placeholder row. The import now walks the entries in `entry_index` order
  directly and hands out fresh positions, which is correct however rekordbox
  numbered them and never invents blank rows.

  This weakness has always been in Mixxx; it only surfaced once the PDB
  row-count fix (`rekordbox-import-fixes.patch`) made playlists actually
  populate — before that they imported mostly empty, so there was nothing to
  misorder.

## Install (on the Pi)

```
sudo ./update-pioneered.sh
```

Re-import the USB after updating (eject and re-insert, or re-open the device)
so the playlists are rebuilt with the fix.

## Field checks

1. On a stick prepared in rekordbox, pick a playlist whose exact order you
   know. Open it in Mixxx: the tracks appear in the **same order as rekordbox
   shows them**, top to bottom.
2. Check specifically that the **last few tracks** of the playlist are at the
   bottom, not floated up to the top.
3. There are **no blank / empty rows** in the list (no untitled entries with no
   artist or duration).
4. The **# column** counts 1, 2, 3 … with no gaps, and sorting by another
   column then back to # restores the playlist order.
5. Track **count** matches rekordbox — nothing dropped, nothing duplicated.
6. Spot-check a **large** playlist (one that spans enough tracks to have been
   worst-affected before) as well as a short one.

If the order still doesn't match rekordbox, the likely explanation is that this
particular export's intended order isn't `entry_index` ascending at all (some
rekordbox versions sort a playlist's display by a different field). In that
case run Mixxx with `--developer` and note the ordering against the PDB so the
sort key can be revisited — the fix is correct for `entry_index`; only the
choice of which field carries the order would be in question.
